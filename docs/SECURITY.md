# M0 security boundary

NOC Workbench runs for one operator on a trusted workstation with literal loopback HTTP and PostgreSQL endpoints. No production targets, remote collectors or vendor integrations exist in M0. An explicitly configured HTTPS origin may name a LAN reverse proxy; this does not change the private HTTP listener or database endpoint.

For LAN access, terminate TLS at a dedicated same-host Nginx listener and restrict access to approved clients with host firewall rules and proxy access controls. Set `NOC_BASE_URL` to the exact browser origin, omitting port 443 and including any nondefault port. Use a canonical lowercase DNS name or IP address without a path. The proxy must preserve the original Host including its nondefault port. Forwarded headers do not select application origin, authentication identity or client authorization; the application ignores them. Overwrite client-supplied forwarding headers at the proxy. All processes on the trusted local host can reach the loopback backend; local administrator compromise is outside this boundary.

Persist the database password and operator hash in a root-readable configuration file outside the repository; never regenerate either on ordinary startup. Keep the database volume across restarts. TLS leaf keys and mkcert CA keys also belong outside the repository with restrictive permissions. Only distribute the public CA certificate to approved clients, verify its fingerprint through a trusted channel, and install it in their OS/browser trust stores. Never distribute the CA private key. LAN deployment acceptance requires actual client connectivity and browser trust evidence in addition to server-local TLS tests.

The operator supplies a bcrypt password hash through environment configuration. Passwords are never stored. Random 256-bit session identifiers are stored only as SHA-256 digests in PostgreSQL; separate random CSRF secrets are bound to sessions. Cookies are host-only, HttpOnly and SameSite Strict, with Secure enabled for HTTPS origins. All POSTs require the exact configured Origin and a valid CSRF token, including login/logout. Host validation rejects DNS-rebinding-style Host changes. Templates escape operator content, request bodies are capped and security headers restrict content, framing and referrers.

Database credentials, session identifiers and CSRF secrets remain sensitive. Protect the workstation, process environment, database volume and backups. The application logs fixed, sanitized lifecycle errors and no request bodies/headers/URLs. It does not offer MFA, distributed rate limiting or an enterprise identity provider. Local login attempts are rate limited; a hostile local process with operator privileges is outside this boundary. Forgotten passwords are reset by supplying a newly generated hash and restarting; changing the configured password hash invalidates prior sessions because their lookup digests are bound to that hash.

Keep migration backups and binaries paired. SQL migrations are application-owned local writes; monitored customer DBs are not accessed. Future inventory must enforce ownership in schema constraints, and future collections must retain the four independent state dimensions described in DATA_MODEL.md.
